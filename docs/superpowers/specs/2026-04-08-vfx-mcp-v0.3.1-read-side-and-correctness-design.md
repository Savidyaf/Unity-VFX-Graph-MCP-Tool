## 1. Background

`v0.3.0` was tagged on 2026-04-07 with 107/107 tests green and 11/13 release-gate criteria PASS. The first downstream agent that tried to use the addon hit a hard usability wall on 2026-04-08:

1. **No way to enumerate existing nodes in a graph.** `vfx_graph.get_info` returns only `graph_path` and `child_count`. There is no `list_nodes`, `list_children`, or equivalent. The addon's mutating actions all return tokens minted at *creation* time, but there is no read-side way to *recover* tokens for nodes the agent didn't create.
2. **Graph-level setting stubs return `"Lane 4B pending"`** instead of either working or returning honest `not_implemented` envelopes.
3. **Catalog read-side stubs**: `vfx_diag.list_attributes` and `list_settings` return empty arrays.
4. **`compilation_status` returns `"unknown"`** with no indication that the action is unimplemented.

The downstream agent's workaround was to add **parallel independent systems** to the same VFX asset rather than enhancing the existing one — a strategy that does not scale and is not a real solution.

Cross-checking the agent's complaint against the v0.3.1 backlog (`docs/superpowers/specs/2026-04-07-rebuild-phase4-review.md` sections 2 and 6, plus `docs/handover-vfx-graph-mcp-rebuild.md` P-sections):

## 2. Architectural premise

The fix is bounded by a single principle:

> The kernel surface needs a read-side enumeration entry point and a write-side `move` entry point that don't exist today, plus the response-shaping chokepoint needs to support write-op metadata.

Everything else in scope is downstream consequence-fixing built on existing kernel surface. The architectural change is **three new contract methods + one new record class**, applied as a single atomic commit to the locked `VfxKernelContracts.cs`. The downstream consumer wiring fans out into two parallel-shaped lanes (read-side and correctness) that run sequentially via subagent dispatch.

### 2.1 Three contract additions (single locked-file commit)

```csharp
// In IVfxNodeOps:
IReadOnlyList<VfxNodeListEntry> ListNodes(string graphAssetPath);
void MoveNode(string graphAssetPath, string token, UnityEngine.Vector2 position);

// In IVfxResponseShaper:
object ShapeMutation(VfxCommitResult commit, bool verbose, JObject mutationPayload);

// New record class in the same file:
internal sealed class VfxNodeListEntry
{
    public string Token;
    public string TypeFqn;
    public UnityEngine.Vector2 Position;
    public string ParentToken;     // null for top-level (graph children)
    public string Category;        // "context" | "operator" | "block" | "parameter" | "subgraph_ref"
    public int    BlockIndex;      // -1 unless Category == "block"
}
```

These are the **minimum** surface additions needed for scope C. F3 (`GetInfo` expansion), F4 (`compilation_status` stub), F10 (catalog attributes/settings), F5 (Shaper consumers), F7 (coercer dispatch), F9 (batch dispatch) all build on existing kernel surface and do not need contract changes.

### 2.2 Token recovery semantics for `ListNodes`

`IVfxIdentity.Mint(graphGuid, model)` is dual-purpose per the Phase 3 fingerprint design — it mints a fresh token if no sidecar record matches the model's structural fingerprint, and recovers the existing token otherwise. `ListNodes` walks `VFXGraph.children`, recurses one level into `VFXContext.children` for blocks, and calls `Mint` for every model encountered.

**Consequence:** Tokens for nodes the user never explicitly added through MCP will be **freshly minted on first `list` call** and persist via the sidecar — that's the same recovery semantics existing graphs already use during YAML verification. There is no separate "discover" path; `Mint` is the only token-issuing primitive.

### 2.3 Top-level fingerprint rule preserved

Per handover note (d): nodes whose direct parent is `VFXGraph` get `parentFp = 0`. `VfxIdentity.Mint`, `VfxStructuralFingerprint.Compute`, and the recovery filter all enforce this. `ListNodes` does **not** bypass — it just hits the same code path with the same parent-fingerprint inputs.

### 2.4 No reflection on `UnityEditor.VFX.*` types

Confirmed: `VFXGraph.children`, `VFXContext.children`, `VFXModel.position`, `VFXModel.GetType()` are all public. The walker can stay reflection-free per the Phase 5-6 `VfxNoReflectionTests` analyzer. The reflection rule targets *runtime type-based dispatch*, not field-attribute reflection used by the catalog generator (which is build-time only).

### 2.5 Soft-fork patches untouched

None of the in-scope work needs new bridge helpers in `Packages/com.unity.visualeffectgraph/Editor/VfxMcpKernelHelpers.cs`. The existing `LoadGraphFromAsset` is the only entry point we use. The two soft-fork patch files stay as-is. **Exception:** A4 (catalog attributes) may require a new bridge helper IF `VFXAttributesManager.GetBuiltInNames()` is unreachable from the addon's editor assembly; that decision is made at impl time and only with the user's explicit approval.

## 4. Risks & contingencies

### 4.1 Risk — A4 (F10 catalog attributes/settings) — HIGH

**What could go wrong:** The walker traverses `VFXLibrary.GetOperators()`/`GetContexts()`/`GetBlocks()`. Pulling **attributes** requires either `VFXAttributesManager.GetBuiltInNames()` (which is internal to `Unity.VisualEffectGraph.Editor` — needs verification that the existing InternalsVisibleTo grant is sufficient) or hard-coding the built-in attribute list (brittle across Unity versions). Pulling per-type **settings** requires reflecting on each `VFXModel` subclass's `[VFXSetting]`-attributed fields — allowed because `[VFXSetting]` is a public attribute and field-metadata reflection is build-time, not runtime.

**Cheap probe before committing:** Lane A subagent's first action on item A4 is to `mcp__jcodemunch__search_symbols` for `VFXAttributesManager` and `[VFXSetting]` in `Packages/com.unity.visualeffectgraph/`, then pick the highest of three paths:

- **Path A4-full** — both surfaces accessible from the addon → emit both arrays, regenerate `VfxCatalog.g.cs`, paged tool dispatch.
- **Path A4-settings-only** — only `[VFXSetting]` reachable → emit `Settings[]`, leave `Attributes[]` empty, `list_attributes` returns `state="not_implemented"`.
- **Path A4-stub** — neither reachable without a new bridge helper → both stubs return `state="not_implemented"`. Catalog regeneration is dropped from this run; F10 stays open.

**Decision rule:** Subagent picks the highest path that does NOT require touching `VfxMcpKernelHelpers.cs`. Adding a new bridge helper raises the soft-fork-patch maintenance burden — only worth it if Path A4-stub is the alternative AND the user explicitly approves a bridge addition. **Default: Path A4-stub on any sign of fragility**, with a written explanation in the subagent report.

### 4.2 Risk — A5 (`@graph` SetSetting dispatch) — MEDIUM

**What could go wrong:** Graph-level settings are heterogeneous: `space` and `boundsSettingMode` are properties on `VFXGraph`; `capacity` is per-context (lives on each `VFXBasicInitialize`); `bounds` is also per-system. The current `set_capacity`/`set_bounds`/`set_space`/`set_data_settings` all call `NodeOps.SetSetting(path, "@graph", name, value)` and catch `NotImplementedException` — implying the original design assumed they all dispatch through one synthetic `@graph` token. That assumption is wrong for `capacity` and `bounds`.

**Decision rule:** Lane A subagent implements only `set_space` end-to-end (the simplest, graph-property-only case) and audits the other three:

- `set_space` — implement.
- `set_data_settings` — implement IF the named setting is a `VFXGraph` field; otherwise return `state="not_implemented"` with `hint="data settings live on individual systems; use vfx_node.set_setting on the relevant context token"`.
- `set_capacity` — change to `state="not_implemented"` with hint pointing to `vfx_node.set_setting` on a `VFXBasicInitialize` context.
- `set_bounds` — same treatment as `set_capacity`.

This converts dishonest `"Lane 4B pending"` stubs into honest `"not_implemented"` stubs with actionable hints, while shipping `set_space` for real.

### 4.3 Risk — B3 (F9 batch dispatch) — MEDIUM

**What could go wrong:** Each tool's `HandleCommand` is structured as `try { switch(action) { case → private helper that opens its own transaction } } catch { ... }`. The refactor extracts the per-action body into an inner helper that takes `scope` instead of opening one. Risk: subagent gets indentation wrong on 8 files in a row, or forgets `scope.Record(...)` calls.

**Mitigation:** Lane B subagent does **one tool at a time** and runs the test suite after each tool. Compile time + test suite (~30s) is small vs. debugging an 8-file regression.

**Fallback:** If F9 spirals, Lane B subagent finishes the 4 domain tools (`vfx_node`, `vfx_block`, `vfx_property`, `vfx_subgraph` — the four the smoke test exercises) and leaves `vfx_asset`/`vfx_diag`/`vfx_graph`/`vfx_recipe` with the existing `NotImplementedException("v0.3.1 batch integration")` stub. The 4 domain tools cover ~90% of real batch usage. F9 stays partially open with a precise note in the review doc.

### 4.4 Risk — Contracts bump leaves the build broken between commits

**What could go wrong:** Lane 0's commit RED's the build. If Lane A subagent fails or reports back malformed, the repo sits broken until Lane B starts.

**Mitigation:** Main agent does NOT advance to Lane B until Lane A's commit lands AND tests pass. If Lane A blows up, main agent reverts Lane 0 with `git revert HEAD` (NOT `reset --hard` — preserves audit trail) and reports back to the user before proceeding. Lane B has the same gate.

**Operationally:** Main agent runs `mcp__UnityMCP__run_tests` between every lane and refuses to dispatch the next lane until tests pass.

### 4.5 Risk — Sandbox commit blocking for subagents

**What could go wrong:** Per handover note (i), subagents during Phases 3/4 hit hard sandbox blocks on `git commit`/`reset`/`stash`. Same applies to v0.3.1 subagents.

**Mitigation:** Each lane prompt explicitly says: "Do NOT call `git commit`, `git reset`, `git restore --staged`, or `git stash`. Use `git add <pathspecs>` only. End your final report with: (1) the exact files you staged, (2) your suggested commit message, (3) any tests you ran and their output." Main agent commits per lane using `git commit --only -- <pathspecs>` from the report.

## 8. Hard constraints (from handover §"Hard constraints")

1. No runtime reflection on `UnityEditor.VFX.*` / `UnityEngine.VFX.*` in `Editor/Kernel/` or `Editor/Generation/`. `VfxNoReflectionTests` enforces this.
2. All 9 tools expose `internal static object ApplyInTransaction(JObject opParams, VfxTransactionScope scope)` with identical signature.
3. Mutating actions go through `VfxBusyGate.EnsureIdle()` first, then a `VfxTransaction` from `VfxKernelContainer.Transaction.Begin(...)`. Read-only actions skip both.
4. Three-part health gate runs at `VfxTransaction.Commit()` only.
5. Terse mode (default `verbose=false`) MUST omit the `health` key.
6. All response shaping goes through `VfxKernelContainer.Shaper`.
7. Kernel contracts are LOCKED — Lane 0 is the ONLY contracts-touching commit in this run.
8. Asset creation goes through `VfxMcpKernelHelpers.CreateVfxAsset` / `CreateVfxSubgraphBlock` / `CreateVfxSubgraphOperator`.
